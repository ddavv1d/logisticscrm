01

Главный вывод

Строим простую операционную CRM на замену Excel, а не «мини-CargoWise». Шесть исследователей и три аудитора независимо сошлись на одном ядре — это сигнал низкого риска.

Контейнер▸ Плечи▸ Журнал стадий▸ Деньги по плечам

Технические решения совпали с твоими прошлыми граблями: статус — VARCHAR + CHECK (не Postgres enum), деньги — Decimal, ручная смена стадий, RBAC в сервисном слое, FCL сейчас — LCL только заложить в схему.

02

Стадии коридора

Дефолтный каталог (Python-константа). Менеджер выбирает стадию в 1 клик. Это не конечный автомат — груз можно вернуть на таможню или откатить: свободный выбор, порядок нужен только для наглядной отрисовки.

    Забронировано место / паром
  2. 02Загрузка контейнера
    Выдан порожний, погрузка у отправителя в Грузии
  3. 03В пути по ж/д: Грузия → Баку / Алят
    Плечо 1 · Azerbaijan Railways (ADY)
  4. 04Прибыл в Баку / Алят + таможня Азербайджан

  5. 05Ожидание парома в Аляте точка простоя
    Отдельная заметная стадия — здесь груз реально застревает (1–7 дней). Владелец увидит «застряло» именно тут.
  6. 06На пароме через Каспий
    Плечо 2 · Алят → Туркменбаши
  7. 07Прибыл в Туркменбаши / выгрузка

03

Рекомендованная модель данных

PostgreSQL. Четыре главные сущности + два справочника + пользователи. Каждое поле выделенным — ключевое решение по оси «просто ↔ гибко».

container Контейнер / Заказ

Центральная сущность — одна запись перевозки. FCL: client_id заполнен. Задел под LCL: NULL + is_consolidated, без таблицы cargo_item.

ref_nocontainer_no (ISO 6346)container_typeclient_id?is_consolidatedcurrent_stage_codecurrent_stage_sinceis_flaggedstatus (soft-delete)

leg Плечо маршрута

Упорядоченный участок: один транспорт, перевозчик, сроки, стоимость. Отдельная таблица (не JSON) — по плечу нужны деньги и агрегация «где застряло».

container_idseq (UNIQUE)transport_typefrom/to_locationcarrier_id?planned_dep/arractual_dep/arr

stage_event Журнал стадий

Сердце системы. Append-only лента: каждая смена стадии = неизменяемая запись. Только INSERT.

container_idstage_codechanged_at (авто)changed_by (авто)commentactual_date?

charge_line Деньги по плечу

income (клиенту) / expense (перевозчику). Маржа = Σ income − Σ expense по контейнеру.

container_idleg_id?kindamount (Decimal)currency=USDis_estimatedpayment_statusdue_date

client / carrier Справочники

Клиент (плательщик) и перевозчик (кому платим на плече). Минимальные.

idnameконтакты

users Роли

3 роли + флаг видимости денег. Argon2id для паролей.

role (CHECK)can_see_moneypassword_hash
04

Что входит в MVP — по трём ролям

Аутентификация обязательна для всех: без входа нет автора у записи стадии, а это ядро брифа.

🧭

Менеджер

вводит всё, двигает стадии
  • Плотная таблица + чипы-счётчики: [В пути 42] [Ожидание парома 7] [Застряло 3⚠]
  • Создание заказа в 2-3 клика: кнопка «Шаблон Средний коридор» → 4 плеча сразу
  • Смена стадии из строки: клик → поповер, дата/время/автор автоматически
  • Карточка с append-only лентой истории (кто / когда / что / комментарий)
📊

Владелец

проверяет, берёт выгрузки
  • Где деньги — к получению / просрочено / маржа за период
  • Где застряло — список контейнеров без движения дольше порога
  • Сколько в пути — разбивка по текущему плечу коридора
  • Лента «что изменилось» + любая цифра кликабельна (drill-down)
🧮

Бухгалтер

деньги и расчёты
  • Строки income / expense по плечу, авто-маржа по контейнеру
  • Флаг estimated / actual — ловит поздний демередж
  • Статус оплаты + due_date, плоский список «кто должен»
  • Одна валюта (USD default), экспорт в 1С / QuickBooks

Инфраструктура MVP: экспорт в Excel/CSV как видная кнопка на каждом списке (выгружает текущий фильтр) · Alembic + сид с 1-го дня · soft-delete/архив вместо удаления · единая транзакция смены стадии.

05

Что берём из реальных решений · что сознательно не делаем

✓Берём

  • Каноничная последовательность вех (Tradlinx / Tier2Systems) — сокращённая под ручной ввод
  • Набор полей карточки из ж/д накладной CIM/SMGS — только то, что вводит диспетчер
  • Валидация check-digit ISO 6346 при вводе номера контейнера — защита от опечаток
  • Разделение «заказ ↔ плечи ↔ статусы ↔ затраты» из open-source TMS (OpenTMS / Odoo)
  • Живой набор документов коридора (T1, CMR, SMGS) от форвардеров Sofmar.ge, RealTrans.ge

✕Не делаем

  • Трекинг / GPS / карта / интеграции (ADY, паром, AIS, EDI) — прямой запрет заказчика
  • Postgres ENUM — только VARCHAR+CHECK + Python-константы
  • Мультивалютную машинерию в v1 — одна колонка currency=USD
  • Полную бухгалтерию (план счетов, проводки, GL, aging/DSO) — отдаём экспортом
  • Таблицу cargo_item и UI сборного груза (LCL) на старте — только задел в схеме
  • Конечный автомат стадий, kanban, drag-drop, RBAC-движок — во Фазу 2
06

Топ-риски и как лечим

Риск №1 — главный

Паралич от объёма («Фаза 2 в маске MVP»). Известная грабля: вязнешь на хендофф-ТЗ и плодишь планы вместо кода (PKUonline / TourCRM месяцами в «Фазе 0»).

Лечим

Брать пересечение мнений, а не сумму. Жёсткий вертикальный порядок сборки, каждый пункт = рабочий E2E-срез. Не писать хендофф-ТЗ — двигать код.

Риск №2

Рассинхрон «текущая стадия ≠ последняя запись журнала», если денормализацию размазать по эндпоинтам.

Лечим

Единственная сервисная функция: атомарно INSERT event + UPDATE current_stage в одной транзакции. Журнал только INSERT.

Риск №3

Продукт проиграет Excel по скорости ввода и поиска — люди вернутся в Ctrl+F.

Лечим

3 дешёвые must-have: пресет маршрута (2-3 клика), видимый поиск+чипы, бейдж «застряло». Дедлайны краснеют — чего Excel не умеет.

Риск №4

Неоднозначная единица учёта (контейнер vs заказ клиента) → владелец не поверит цифрам.

Лечим

Зафиксировать: первичен контейнер, деньги/маржа на контейнер; заказ клиента = фильтр/представление.

Риск №5

Утечка маржи менеджеру — или переписывание всех эндпоинтов ради сокрытия позже.

Лечим

Один флаг can_see_money + разная сериализация list-эндпоинта по роли. Не field-level RBAC.

08

9 вопросов к тебе перед стартом кода

Ответы на них определяют модель данных и границу MVP. Отвечай коротко — по каждому у меня уже есть дефолт, если промолчишь.

1
Направление: только Грузия→Узбекистан, или нужны обратные рейсы? Влияет на двунаправленность каталога стадий.
2
Валюта: платежи по плечам бывают не в USD (GEL/AZN/TMT/UZS/RUB)? Часто? Мультивалюта в v1 или Фаза 2.
3
Единица учёта: подтверждаешь, что первичен КОНТЕЙНЕР (деньги/застревание на контейнер), а заказ клиента = фильтр?
4
LCL/сборный: насколько скоро реально нужен? «Через год» → прячем; «скоро» → планируем экран cargo_item.
5
Финансы: хватит плоских строк + «кто должен», или бухгалтеру нужен инвойс-документ (номер/дата/частичные оплаты) сейчас?
6
Авто-плечи (склад→порт, станция→склад): нужны в маршруте, или заказы начинаются/кончаются на станции/в порту?
7
Порог «застряло»: единый для всех, или свой на плечо (на таможне 5 дней норма, на пароме 5 дней = проблема)? Нужны пуши?
8
Каталог стадий: подтверждаешь эти 10-11 стадий? Нужна ли владельцу возможность самому их редактировать (тогда каталог = таблица+админка)?
9
Документы: хранить сканы файлов (инвойс, packing list, SMGS, коносамент), или достаточно НОМЕРОВ документов для поиска?
