# Предпроектный анализ — CRM для контейнерной логистики (Средний коридор)

> Результат работы совета из 10 агентов (6 исследователей + 3 аудитора + 1 председатель).
> 153 веб-поиска, изучены реальные TMS/форвардеры маршрута Грузия→Узбекистан.
> Дата: 2026-07-31.

---

## 🎯 Главный вывод

Строим **простую операционную CRM на замену Excel**, не «мини-CargoWise». Шесть исследователей и три аудитора **независимо сошлись на одном ядре** — это сигнал низкого риска:

**4 главные сущности:** `Контейнер → Плечи (legs) → Журнал стадий → Строки денег по плечам`

Ключевые технические решения (совпали с прошлыми граблями Давида):
- статус = **VARCHAR + CHECK**, НЕ Postgres enum (enum не откатывается, значения не удалить);
- деньги = **Decimal**;
- **ручная смена стадий**, БЕЗ трекинга/GPS/интеграций (прямой запрос заказчика);
- **RBAC в сервисном слое** (3 роли), не движок прав;
- **FCL сейчас**, LCL только заложить в схему (`nullable client_id` + `is_consolidated`), НЕ строить `cargo_item`.

**Оценки простоты от аудиторов:** 🦅 Простота 6/10 · 💡 Польза 7/10 · 🔧 Реализуемость 6/10.
Все три сошлись: ядро правильное, риск не в коде, а в **соблазне сложить сумму всех «recommended» и получить средний TMS вместо замены Excel**.

## 🚂 Рекомендованный список стадий (то, что менеджер двигает вручную)

Это **дефолтный каталог** (Python-константа), менеджер выбирает стадию в 1 клик:

1. Бронирование (booking) — забронировано место/паром
2. Загрузка контейнера / выдан порожний (у отправителя в Грузии)
3. В пути по ж/д: Грузия → Баку/Алят
4. Прибыл в Баку/Алят + таможня Азербайджан
5. **Ожидание парома в Аляте** ← отдельная заметная стадия, главная точка простоя коридора
6. На пароме через Каспий (Алят → Туркменбаши)
7. Прибыл в Туркменбаши / выгрузка
8. В пути по ж/д: Туркменбаши → Узбекистан (Ташкент/Навои)
9. Таможенное оформление в Узбекистане
10. Выдан/доставлен клиенту (авто-доставка)
11. [опц.] Порожний возвращён

> ⚠️ Важно: это НЕ конечный автомат. Груз могут вернуть на таможню, паром отменить — менеджер выбирает стадию свободно, порядок нужен только для наглядной отрисовки.

## 🗄️ Рекомендованная модель данных (PostgreSQL)

### `container` — Контейнер / Заказ (центральная сущность)
Одна запись перевозки. FCL сейчас: `client_id` заполнен = 1 контейнер = 1 клиент; `NULL` + `is_consolidated=true` = задел под LCL без создания `cargo_item`. `current_stage_code` денормализован для быстрых списков/дашборда.

Поля: `id`, `ref_no` (внутренний номер, генерим, UNIQUE), `container_no` (ISO 6346, напр. MSKU1234565, опц. валидация check-digit), `container_type` (20'/40'/40'HC/Reefer — dropdown), `client_id` (nullable FK), `is_consolidated` (переключатель FCL/LCL), `origin/dest_location`, `current_stage_code` (денорм.), `current_stage_since`, `is_flagged` (проблема — отдельно от стадии), `status` (active/delivered/cancelled/archived — soft-delete), `created_by/updated_by`, таймстемпы.

### `leg` — Плечо маршрута
Упорядоченный участок с одним видом транспорта/перевозчиком/сроками/стоимостью. Отдельная таблица (не JSON), т.к. по плечу нужны деньги, перевозчик и агрегация «где застряло».

Поля: `id`, `container_id` (FK CASCADE), `seq` (ОБЯЗАТЕЛЕН, UNIQUE с container_id), `transport_type` (rail/sea_ferry/truck/other — VARCHAR+CHECK), `from/to_location`, `carrier_id` (nullable FK), `planned/actual_departure/arrival`, `comment`, таймстемпы.

### `stage_event` — Журнал стадий (сердце системы)
**Append-only** лента. Каждая смена стадии = одна неизменяемая запись.
Поля: `id`, `container_id` (FK), `stage_code`, `changed_at` (авто), `changed_by` (авто, FK users), `comment`, опц. `actual_date` (если факт отличается от момента записи).

### `charge_line` — Строка денег по плечу
`income` (клиенту) / `expense` (перевозчику). Маржа = Σ income − Σ expense по контейнеру.
Поля: `id`, `container_id` (FK), `leg_id` (nullable FK), `kind` (income/expense), `charge_type`, `amount` (Decimal), `currency` (default USD), `is_estimated` (estimated/actual — ловит поздний демередж), `payment_status` (unpaid/partial/paid), `due_date`, `counterparty`, таймстемпы.

### `client`, `carrier` — Справочники
Клиент (плательщик) и перевозчик (кому платим на плече). Минимальные: id, name, контакты.

### `users` — Пользователи + роли
`role` VARCHAR+CHECK (manager/owner/accountant), `can_see_money` (булев флаг — менеджеру не показываем маржу). Argon2id для паролей.

## ✅ Что входит в MVP (по 3 ролям)

**Аутентификация (все):** логин, Argon2id, cookie-сессия + CSRF, 3 роли в FastAPI-зависимостях. Без входа нет автора у записи стадии — а это ядро брифа.

**Менеджер:**
- Список контейнеров: плотная таблица + чипы-фильтры-счётчики сверху `[Все 138] [В пути 42] [Ожидание парома 7] [Застряло 3⚠] [Доставлено 61]`, всегда видимый поиск, кнопки `+ Контейнер` и `Выгрузить в Excel`. Строка «застряло» — янтарная.
- Создание заказа в 2-3 клика: минимальная форма (№ + клиент) + кнопка **«Шаблон Средний коридор»** → одним кликом 4 предзаполненных плеча.
- Смена стадии из строки: клик по бейджу → поповер `→ Следующая: [стадия]` + весь список (можно откатить/перескочить) + опц. комментарий + опц. дата факта. Синхронное сохранение + тост. Дата/время/автор — автоматически.
- Карточка контейнера: вертикальная append-only лента истории (иконка транспорта + что + автор + дата-время + комментарий, новейшее сверху). Текущая стадия — бейдж «Плечо 3 из 5 · Паром Каспий». Блок денег ниже.

**Бухгалтер + владелец (деньги):** строки income/expense по плечу, авто-маржа по контейнеру, флаг estimated/actual, статус оплаты + due_date, плоский список «кто должен». Одна валюта (USD default).

**Владелец (дашборд с drill-down, каждая цифра кликабельна):**
1. **Где деньги** — к получению / просрочено / маржа за период;
2. **Где застряло** — СПИСОК контейнеров без смены стадии дольше порога (перечень, не число);
3. **Сколько в пути** — разбивка по текущему плечу коридора;
4. Лента «что изменилось» — последние N событий по всем контейнерам.

**Инфраструктура:** экспорт в Excel/CSV как видная кнопка на каждом списке (выгружает текущий фильтр); Alembic + сид с 1-го дня; soft-delete/архив вместо удаления.

## 🎁 Что берём из реальных решений

- **Каноничная последовательность вех** (Tradlinx/Tier2Systems: booking→gate-in→loaded→departed→arrived→discharged→customs→gate-out→delivered) — но сокращаем под ручной ввод и адаптируем под 4 плеча TITR.
- **Набор полей карточки** — из официальной ж/д накладной CIM/SMGS (отправитель/получатель/станции/№ контейнера/места/масса) — только те поля, что реально вводит диспетчер.
- **Валидация check-digit ISO 6346** при вводе номера контейнера — дешёвая защита от опечаток.
- **Разделение «заказ ↔ плечи ↔ статусы ↔ затраты»** из open-source TMS (OpenTMS/Odoo) — но без их тяжеловесных авто-фидов и WMS.
- **Живой набор документов коридора** (T1, CMR, SMGS, сертификат происхождения; ветка Поти/Батуми→Алят→Туркменбаши→Ташкент) — от реальных форвардеров Sofmar.ge, RealTrans.ge.

## 🚫 Что сознательно НЕ делаем (переусложнение)

- ❌ Реальный трекинг/GPS/карта/интеграции (ADY, Uzbek Railways, паром, AIS, INTTRA, EDI) — **прямой запрет заказчика**, самая дорогая и хрупкая часть.
- ❌ Postgres ENUM — только VARCHAR+CHECK + Python-константа для каталога стадий.
- ❌ Мультивалютная машинерия в v1 — до одной колонки `currency` (default USD).
- ❌ Полная бухгалтерия (план счетов, проводки, GL, инвойс-консолидатор, aging/DSO) — считаем маржу и долги, бухгалтерию отдаём экспортом в 1С/QuickBooks.
- ❌ Таблица `cargo_item` и UI сборного груза (LCL) на старте — только задел в схеме.
- ❌ Строгий конечный автомат стадий — свободный выбор.
- ❌ Kanban / оптимистичный Undo / массовая смена / drag-drop — во Фазу 2.
- ❌ Конфигурируемый RBAC-движок — 3 зашитые роли + флаг `can_see_money`.
- ❌ House/Master Bill, consignor/consignee/notify, таможенный файлинг, white-label портал, воронка продаж, AI-чтение тарифов, WMS — балласт для 30-150 заказов/мес.

## ⚠️ Топ-5 рисков

| Риск | Как лечим |
|------|-----------|
| **Паралич от объёма** («Фаза 2 в маске MVP»). Известная грабля: Давид вязнет на хендофф-ТЗ и плодит планы вместо кода (PKUonline/TourCRM месяцами в «Фазе 0»). | Брать **пересечение**, а не сумму мнений. Жёсткий вертикальный порядок сборки, каждый пункт = рабочий E2E-срез. **НЕ писать хендофф-ТЗ — двигать код.** |
| Рассинхрон «текущая стадия ≠ последняя запись журнала» | **Единственная** сервисная функция смены стадии: атомарно INSERT event + UPDATE current_stage в одной транзакции. Журнал только INSERT. |
| Продукт проиграет Excel по скорости ввода/поиска | 3 дешёвые must-have: пресет маршрута (2-3 клика), видимый поиск+чипы, бейдж «застряло/просрочено». Дедлайны краснеют — то, чего Excel не умеет. |
| Неоднозначная единица учёта (контейнер vs заказ) → владелец не поверит цифрам | Зафиксировать: **первичен контейнер**, деньги/маржа на контейнер; клиентский заказ = фильтр/представление. |
| Утечка маржи менеджеру | Один флаг `can_see_money` + разная сериализация list-эндпоинта по роли. НЕ field-level RBAC. |

## 🛠️ Рекомендованный порядок сборки (вертикальными срезами)

Каждый срез — рабочий, проверяется E2E через фронт:

0. **Скелет** + auth + сид (стадии, точки, типы зарядов)
1. **CRUD Контейнер + Плечи** с пресетом «Средний коридор»
2. **Смена стадии + журнал** + денормализация current_stage (одна транзакция)
3. **Карточка** контейнера с лентой истории
4. **Деньги** income/expense + авто-маржа (одна валюта)
5. **Дашборд**: в пути / застряло / маржа (drill-down)
6. **Экспорт** xlsx

## ❓ 9 вопросов к Давиду перед стартом кода

1. **Направление:** только Грузия→Узбекистан, или нужны обратные рейсы? (влияет на двунаправленность каталога стадий)
2. **Валюта:** платежи по плечам бывают не в USD (GEL/AZN/TMT/UZS/RUB)? Часто? (мультивалюта в v1 или Фаза 2)
3. **Единица учёта:** подтверждаешь, что первичен КОНТЕЙНЕР (деньги/застревание на контейнер), а заказ клиента = фильтр?
4. **LCL/сборный:** насколько скоро реально нужен? («через год» → прячем; «скоро» → планируем экран)
5. **Финансы:** хватит плоских строк-зарядов + «кто должен», или бухгалтеру нужен инвойс-документ (номер/дата/консолидация/частичные оплаты) уже сейчас?
6. **Авто-плечи** (склад→порт, станция→склад): нужны в маршруте, или заказы начинаются/кончаются на станции/в порту?
7. **Порог «застряло»:** единый для всех, или свой на плечо (на таможне 5 дней норма, на пароме 5 дней = проблема)? Нужны ли уведомления/пуши?
8. **Каталог стадий:** подтверждаешь предложенные 10-11 стадий? Нужна ли владельцу возможность самому редактировать список (тогда каталог = таблица+админка)?
9. **Документы:** хранить сканы файлов (инвойс, packing list, SMGS, коносамент), или достаточно НОМЕРОВ документов для поиска?
