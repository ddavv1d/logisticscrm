# Рабочий процесс и скиллы — LogisticsCRM

> Как вести проект: порядок фаз, дисциплина, когда какой скилл звать, паттерн council.

## Mindset (из опыта Давида)

- **Дизайн тащи из 21st.dev MCP** (`docs/21ST_MCP_GUIDE.md`, бридж `scripts/s21.sh`/`get21.sh`) — не выдумывай, бери готовое и адаптируй под палитру. Search бесплатен и безлимитен.
- **Безопасность с самого начала**, не «потом». gitleaks + security-scan перед коммитом.
- **Trust no agent, including yourself.** Не заявляй «готово» без пруфа (тесты зелёные / скриншот в браузере / E2E прошёл).
- **Одна задача за раз**, без drive-by рефакторингов и батчинга непроверенной работы.
- **ГЛАВНАЯ ГРАБЛЯ (личная):** склонность вязнуть на хендофф-ТЗ и плодить планы вместо кода (PKUonline/TourCRM месяцами в «Фазе 0»). ⇒ **ТЗ уже написано (см. `docs/TZ_SLICES.md`). Дальше — двигать КОД срезами, не переписывать планы.**

## Дисциплина (жёстко)

1. **Верифицируй после КАЖДОГО среза** (`docs/VERIFICATION.md`): билд + тесты + lint/types + security + требования — всё зелёное С ПРУФОМ.
2. **Ветка + diff/PR.** Никогда не коммить в main напрямую, не пушь, не деплой без явного «да» Давида.
3. **Секреты только в env.** `.env` в `.gitignore`, `.env.example` с плейсхолдерами. Ключ 21st — в `~/.claude.json`, НЕ в репо.
4. **Проверяй в браузере** через preview_* инструменты Claude Code — не проси Давида проверять руками.

## Порядок фаз

```
0. Среда ДО кода     → scripts/check_env.sh зелёный (21st бридж, скиллы, tooling). ✅ УЖЕ СДЕЛАНО.
1. Research          → ✅ СДЕЛАНО (совет 10 агентов, research/RESEARCH_SYNTHESIS.md).
2. Дизайн на бумаге  → ✅ СДЕЛАНО (модель данных, стадии, экраны в synthesis + TZ_SLICES.md).
3. Council-ревью     → перед кодом (ревью плана среза) И на финал (ревью готового). Паттерн ниже.
4. Код по срезам     → см. docs/TZ_SLICES.md, срезы 0→6. Backend (модели→API→auth) → Frontend (21st) → seed → E2E.
5. Verify после каждого среза → docs/VERIFICATION.md.
6. Security-gate + council на финал → перед коммитом.
```

**Открытый блокер перед стартом кода:** 9 вопросов Давиду (`research/RESEARCH_SYNTHESIS.md`, секция вопросов / артефакт). По каждому есть дефолт — можно стартовать на дефолтах и уточнить по ходу.

## Скиллы — что и когда звать (через Skill tool)

### Дизайн / фронт
- **taste-skill** ⭐ — применять к КАЖДОМУ экрану. Анти-слоп: «design read» (прочитай тему прежде чем рисовать), регуляторы DESIGN_VARIANCE/MOTION_INTENSITY/VISUAL_DENSITY, запреты AI-tells (AI-фиолетовый, фейковый UI из div, тотальный glassmorphism). Сначала объяви design-read одной строкой, потом код.
  - ⚠️ Правило про em-dash в taste-skill — про АНГЛИЙСКИЙ маркетинг. В русском тире (—) корректно, не ломать родной язык.
  - Сочетание с 21st: 21st даёт СЫРЬЁ (компонент), taste-skill решает СКОЛЬКО уместно. Тема тут — «стальной коридор» (сдержанно, не неон).
- **21st-dev** — рабочий процесс с 21st (search → get → adapt).
- **react-component** — генерация отдельных компонентов под проект.

### Безопасность
- **security-scan** ⭐ — после любого изменения auth/данных и как гейт перед коммитом. Слои: Authentication, Authorization (**IDOR!**), Input validation, Data protection, Infrastructure, Business logic. Находки с severity + фиксом.
  - Всегда рядом: `gitleaks detect` (секреты в коде/истории) отдельной командой.
  - Планка для LogisticsCRM: не PHI, но операционные данные компании (ставки, маржа, клиенты) — scope по роли, анти-IDOR, флаг can_see_money.

### Прочее (по ситуации)
- **use-railway** — если дойдём до демо-деплоя.
- **quick-commit / commit** — аккуратные коммиты (только с согласия).

## Council-ревью (Workflow, НЕ веб-версия)

Запускается как **Workflow** (несколько агентов-линз + chairman-синтез). НЕ путать с llm-council веб-аппом (тому нужен ключ OpenRouter — у нас плейсхолдер). Линзы под ЭТОТ проект:

```js
const LENSES = [
  { key: 'security',    prompt: `security-аудитор. Читай backend/... Ищи РЕАЛЬНЫЕ дыры: IDOR (scope по роли/компании), пропущенные auth-гейты, CSRF, секреты в логах, инъекции, утечка маржи менеджеру. file:line + эксплойт + фикс.` },
  { key: 'engineering', prompt: `senior-инженер. Реальные баги: рассинхрон current_stage↔журнал (одна транзакция?), обработка ошибок, гонки, N+1 на списке контейнеров/плеч, размер бандла. file:line + фикс.` },
  { key: 'ux',          prompt: `UX-ревьюер. Против принципов: смена стадии в 1-2 клика, состояния (loading/empty/error), наглядность «где застряло», чипы-счётчики, тон РУ-копирайта, кнопка экспорта на виду. file + проблема + фикс.` },
  { key: 'domain',      prompt: `эксперт контейнерной логистики (Средний коридор). Проверь: стадии из одного источника (Python-константа, не хардкод), корректность маржи (Σincome−Σexpense на контейнер), единица учёта=контейнер, плечи с seq. file:line.` },
]
// + chairman синтезирует в BLOCKER/SHOULD/NICE punch-list.
```

**Важно:** council находит РЕАЛЬНЫЕ баги — чини блокеры перед «готово». На финале прошлого проекта council нашёл 4 блокера, уехавших бы в прод.
